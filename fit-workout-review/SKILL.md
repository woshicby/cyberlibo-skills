# FIT 训练复盘｜赛博黑影儿

把本地环境检查、验数和复盘视为一条连续工作流。先确认本地 FIT 数据真的可读，再解释这堂课练到了什么。不要把设备指标换一种说法重复一遍。

本 Skill 是独立的社区项目，不代表 COROS 或 Garmin，也不暗示任何厂商对分析结论的认可。数据完全来自用户自己的本地 FIT 文件：不连接云端、不发起 OAuth、不上传任何文件。

## 内置赛博黑影儿框架

本 Skill 已内置 ShadowRunner 与单次跑步复盘直接相关的决策框架，不要求用户另装或调用 `$shadowrunner`。处理训练数据时按以下顺序工作：

1. **先筛风险**：疼痛、胸闷、晕厥、异常气短、持续疲劳等命中时，只做事实整理和风险提示，不设计训练实验。
2. **收集最小上下文**：只问会改变判断的目标、原计划、当前阶段、主观用力感、环境或近期恢复信息；缺失就标为未知，不为做基础复盘强行索取完整画像。
3. **反推前置条件**：从实际完成的训练反推它依赖的基础、恢复和环境，不把一次完成结果当成普遍能力。
4. **判断阶段与瓶颈**：把训练目的放回建立习惯、积累能力、专项准备、维持或恢复等阶段，只保留最多两个有证据的候选瓶颈。
5. **核对适用域与边际收益**：用户引用他人方案、设备建议或要求改变训练时，先检查目标、训练史、环境和恢复条件是否匹配，再比较收益、代价与可回滚性。
6. **给最小可逆下一步并记录**：一次只改变或观察一个关键变量，写清保持不变项、观察指标、复盘时点和停止条件；新反馈出现后更新或推翻原假设。

这套框架只服务于本地 FIT 训练复盘；单次活动不能单独证明长期进步、退步或能力上限。

## 入口判断

先判断用户处于哪一步：

1. **FIT 目录已能列出活动**：直接做最小读取检查，不讲环境。
2. **目录已配置但没有 .fit 文件**：确认目录路径是否正确、同步任务是否运行，不要猜。
3. **没有可用目录**：只问一句 FIT 文件夹在哪里（或让用户自己同步到默认位置），不要索取完整目录树。
4. **目录可用但 Python 依赖缺失**：读取 `references/fit-data-sources.md` 的「环境准备」，按用户操作系统给一条 venv 命令，一次只引导一步。
5. **数据可读**：进入单次跑步复盘。
6. **用户只想配置**：通过最小读取检查后停止，不擅自读取更多训练或健康数据。

## FIT 目录配置

FIT 文件夹位置按以下优先级解析，优先级高的覆盖低的：

1. **命令行参数** `--dir <路径>`：单次使用，不写入任何文件。
2. **环境变量** `FIT_WORKOUT_REVIEW_FIT_DIR`：适合在 agent 配置或 shell 配置中固化。
3. **默认值**：用户主目录下的 `FIT` 文件夹。

规则：

- 永远不要把某个具体机器的绝对路径写死进本 Skill 或仓库文档示例之外的任何地方。
- 用户说“我的 FIT 文件夹”但没有给路径时，先试默认值与环境变量；都不可用时只问一次路径。
- 路径解析失败时明确说“找不到该目录”，并给一个用户可直接核对的修正动作，不要扫全盘。
- 目录只允许列出和读取 `.fit` 文件；不写入、不移动、不重命名、不删除任何文件。

## 环境准备

`scripts/fit_reader.py` 只依赖标准库 + `garmin-fit-sdk`。按项目惯例为每台机器建独立 venv：

```text
Windows:  python -m venv .venv-windows && .venv-windows/Scripts/python -m pip install -r scripts/requirements.txt
macOS:    python3 -m venv .venv-macos && .venv-macos/bin/python -m pip install -r scripts/requirements.txt
```

venv 建在 skill 目录内（`.venv-windows` / `.venv-macos`），已被 `.gitignore` 排除，不随仓库分发；每台机器自建，互不兼容也互不影响。字段语义与命令参考见 `references/fit-data-sources.md`。

## 最小读取检查

执行顺序：

1. 用 `list` 确认目录里有可解析的 `.fit` 文件（默认最近 14 天、最多 10 条摘要）。
2. 若用户已经要求复盘，读取最近 14 天、最多 3 条跑步摘要；否则先说明“将只读取最近一条运动摘要用于验证”，取得同意再读。
3. 只在内部使用文件名作为定位标识；文件名中的城市、赛事名等描述信息只在用户主动询问时提及。
4. 验证成功只说：“本地 FIT 可读，可以列出活动并做复盘。”不要展示完整文件列表。
5. 若 14 天为空，先问最近一次跑步大致日期，再按用户提供的范围查询；不要自动扫完整历史。

## 选择目标活动

- 用户给出日期、训练名或结构时，优先按文件名条件定位（文件名格式：`YYYYMMDD-HHMMSS-运动类型[-描述]-活动ID.fit`）。
- 用户说“今天”“昨天”时，使用用户时区；不确定时先确认时区或当地日期。
- 用户只说“最近一次”时，选择最新跑步活动，不把骑行、步行或力量训练混入。
- 同一日期有多条候选时，只列日期、开始时间、距离、时长和运动类型，请用户选；始终忽略并隐藏地点。
- v1 只正式复盘单次跑步。其他运动可以读取，但要说明方法尚未针对该项目校准。

## 数据读取梯度

始终从最小数据开始（每条命令对应 `scripts/fit_reader.py` 的一个子命令）：

1. **记录摘要**（`list`）：定位活动。只给文件名、日期、运动类型、大小，不打开文件。
2. **活动详情**（`summary`）：读取距离、时长、配速/速度、心率、功率、步频、步幅、爬升、环境温度和 `workout_steps`（结构化训练段），并返回每个数据域的完整性状态（`ok` / `partial` / `missing` 与覆盖率）。若文件名含 `@` 课表标注（如 `3×(20s@436-425_60s)`、`@149-157`、`@E`），`summary` 额外返回 `name_alignment`：把文件名标注解析后与 `workout_steps` 逐段核对，供复盘引用。
3. **分圈/分段**（`laps`）：识别热身、主训练、恢复、放松和后程变化。自动分圈（`lap_mesgs`）与结构化训练段（`workout_steps`）分开呈现，不混写。
4. **自定义时间窗**（`window`）：仅在用户明确问“最后 20 分钟”“第二组 15 分钟”等问题时使用，并控制采样点数。

不要默认读取与本次问题无关的活动、健康数据或完整记录流。用户明确请求且与问题直接相关时，才扩大到相应范围。精确 GPS（含经纬度、半圆原始值）、完整路线、地图、起终点始终不读取、不请求、不展示，即使用户明确要求也不例外；`fit_reader.py` 本身不输出任何坐标字段。

## 数据完整性检查

分析前核对 `summary` 返回的 `quality` 与 `derived`：

- 单位和时区是否一致（开始时间来自文件内时区偏移，无偏移时按 UTC+8 并在置信度中说明）；
- 距离、活动时间、移动时间与暂停是否合理；
- 心率、功率、步频、速度、海拔、温度各字段是 `missing`、`partial` 还是 `ok`，覆盖率多少；
- `workout_steps`（结构化训练段）与 `lap_mesgs`（自动分圈）是否互相矛盾，比如目标 3 组实际只出现 2 个恢复段；
- 室内跑、越野、明显爬升、红绿灯或 GPS 漂移是否限制配速解释；
- 设备给出的训练标签（文件名/运动类型）是否与分圈事实一致。

发现异常时保留原值，解释它为何限制结论。不要擅自修正或补齐。`partial` 字段的结论要降低置信度；`missing` 字段不得用于任何数值判断。

### 间歇结构识别

间歇类复盘优先以 `workout_steps` 为第一证据：

- `intensity: rest` 的段即组间恢复段，其 `duration_time_s` 是恢复时长；
- `target_type: speed` 的 `target_pace_s_per_km` 是目标配速区间；`target_type: heart_rate` 的 `target_heart_rate` 是目标心率区间；
- `repeat_steps` 是重复次数；
- 用 `laps` 里实际各圈的配速/心率对照目标值，判断“跑进了目标区间还是掉出了”。

设备目标与实际执行不一致时，分别陈述两者，不自动判谁对。

**文件名课表标注（`name_alignment`）**：文件名里的 `@` 标注（如 `35min3×(20s@436-425_60s)`、`40min@127-159 6×10s_110s`、`10×800@430_3min`、`1×10min@E`）是用户自己写的课表简写，`summary` 的 `name_alignment` 已把它解析并与 `workout_steps` 对齐：

- 数值标注按范围判别：`100-199` = 心率（bpm，人基本不可能跑到 1 分多/公里），`300-999` = 紧凑配速 `m:ss`（`436` = 4:36 = 276 s/km），`200-299` 两者皆可能、标低置信；带小数的 `2.0-2.5` = 心率分区（不是配速/时间），分区↔bpm 映射随静息/最大心率变化、FIT 未存分区边界，不与 bpm 对齐、只与设备段实测心率区间并列陈述；
- 字母 `E/M/R` 是区间标签，中文（如“法特莱克”）是文字标注，不与数值对齐、只给设备段目标供参考；
- `@` 前 `×` 后是工作段（`20s`/`800`/`10min`），目标后 `_60s`/`_3min` 是恢复段；
- 引用时**以 `workout_steps` 为目标基准、文件名标注为用户意图基准**，两者不一致（如文件名标 20s、设备记录 30s）时分别陈述并注明，不自动改判哪边对；`name_alignment.aligned=false` 的段要降低该结论的置信度。

## 可选 OpenWeatherMap One Call API 4.0 环境补全

这是一条显式授权的降级路径，不是默认数据源，也不是完成复盘的必选项。用户只想配置时，只完成 key 的本机配置检查，不读取任何 FIT 文件；用户没有明确同意把本次活动的粗略地区和时间发送给第三方时，不发起天气请求。

1. **先判定是否需要**：优先使用 `summary` 里 `quality.env.temperature` 状态为 `ok` 的 FIT 温度（含均值/最小/最大）。FIT 只有温度没有湿度：温度可信时，湿度缺失直接标“湿度未知”，不因此发起天气请求；仅当温度 `missing`/`partial` 且用户需要环境上下文时，才进入补全。
2. **可选配置 key**：安全检查 `OPENWEATHERMAP_API_KEY`。若未配置，先说明天气 API 完全可选，只问用户是否需要配置；用户愿意时读取 `references/openweathermap.md`，一次只引导一个配置动作。key 只能来自客户端 secret、本机密钥管理器或进程环境；不向用户索取、回显、写入文件、命令参数、URL 可见输出或日志。
3. **人工温湿度兜底**：key 未配置、用户拒绝配置、宿主无法安全保存 key、用户拒绝第三方查询，或 API 最终失败时，改问：“这次运动时大约多少摄氏度、湿度大约多少？不清楚可以直接说不知道。”这同样不强制；用户提供时标为“用户提供的环境信息”，不伪装成设备或天气 API 实测；不知道时保留环境未知并继续复盘。
4. **取得单次同意**：仅在 key 已安全配置且准备调用 API 时，说明将发送约 `0.1°` 粗化位置和活动 UTC 时间窗给 OpenWeatherMap；key 已配置不等于位置授权。用户拒绝时转入人工温湿度兜底，不反复劝说。
5. **调用历史时间线**：历史活动使用 One Call API 4.0 的 `timeline/1h`，以活动开始时间作为 `start`，`units=metric`，只请求覆盖本次活动的最小窗口；禁止用 `/current` 代替历史数据。宿主允许本地执行时优先使用 `scripts/openweather4.py`，它会再次将坐标粗化并只返回温湿度记录。
6. **合并但不伪造**：保留 FIT 原值、OpenWeatherMap 值和用户提供值的来源标签。只补空缺或并列展示，不覆盖可信原值；没有足够接近的小时记录或响应不完整时仍记为未知。把 API 结果标成“外部天气上下文 / 约略位置估计”，把用户回答标成“用户提供的环境信息”，均不得写成跑者实测或确定的疲劳原因。
7. **错误即降级**：401/403、429、超时、5xx 或字段异常最多重试一次，随后转入人工温湿度兜底并继续原有复盘；不暴露 key，不把错误堆栈或完整请求 URL 展示给用户，也不因补天气失败而扩大 FIT、GPS 或健康数据读取范围。

## 复盘方法

详细方法见 `references/review-methodology.md`，其中包含本 Skill 已内置的 ShadowRunner 训练决策链。核心顺序不可跳过：

1. **先筛风险并确认上下文**：命中健康警讯时停止训练实验；目标、原计划或阶段未知时降低结论强度。
2. **还原训练结构**：优先用 `workout_steps`，缺失时用 `laps` 的配速/心率形态推断；无法识别就标“结构未知”。
3. **判断训练目的与阶段**：轻松、有氧、渐进、阈值、间歇、长距离、比赛或未知；设备标签只能作旁证。
4. **区分输出与代价**：配速/功率描述输出，心率描述生理反应；两者变化不同步时只列候选解释。
5. **看稳定性并定位瓶颈**：比较相同训练段，不拿热身平均值和主训练硬比；只保留最多两个有证据的候选。
6. **核对适用域与边际收益**：不把他人方案、设备建议或单次结果直接外推到用户；同时计入恢复、时间和失败后的回滚成本。
7. **给一个最小可逆下一步**：优先观察点、记录方式或复盘问题，不直接下个体化训练剂量。
8. **记录并更新**：保留预期、实际、代价、停止条件和被支持/推翻的假设。

把内容分为三层：

- **事实**：`fit_reader.py` 直接返回或可计算验证的数值。
- **解释**：由多个事实支持的判断。
- **假设**：还需要天气、主观体感、伤痛、抽象路线类型或近期训练才能验证的可能性。

任何因果句都要能回答“证据来自哪里”。只有相关性时写“同时出现”或“可能有关”，不要写“导致”。

### 训练结构
- 热身：...
- 主训练：...
- 恢复 / 放松：...

### 关键证据
1. ...
2. ...
3. ...

### 做得好的地方
...

### 当前主要问题
...

### 下一步
一个低风险、可回滚、可验证的观察或行动方向；说明保持不变项、观察指标、复盘时点和停止条件。

## 安全与隐私边界

执行 `references/privacy-safety.md`：

- 不做医疗诊断、伤病判断、用药或营养处方。
- 不给个体化周跑量、精确配速、心率区间、间歇组数或恢复天数处方。
- 用户报告胸痛、晕厥、异常气短、持续或加重疼痛等情况时，停止训练实验建议，建议及时寻求合格专业人员评估；紧急症状按当地急救流程处理。
- 不承诺比赛成绩，不把预测值写成事实。
- 文件名只作为活动定位的临时 opaque selector；其中的活动 ID、城市、赛事名不主动向用户展示，不写入任何对外内容。
- 始终不展示精确起终点、地图、完整路线、坐标或 FIT 文件内容中的位置字段；`fit_reader.py` 的输出已按此边界裁剪，不要绕过脚本直接解析原始 record 中的位置字段。
- 不模仿真实人物的固定口头禅、私密经历、语气指纹或人格。

## 失败时如何结束

无法继续时，明确给出：

1. 已确认到哪一步；
2. 卡在哪一层：目录配置、Python 依赖、文件可解析性或数据质量；
3. 用户现在只需做的一个动作；
4. 哪些内容不要发送给你（完整目录树、文件内容、坐标、健康数据）。

不要用“再试试”代替诊断，也不要在读取未验证时开始编造训练复盘。
